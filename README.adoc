= Libmw

Libmw is a modular C++23 utility library providing wrappers and helpers for common tasks such as HTTP networking, database access, cryptography, and system execution.

== Modules

The library is split into several optional components:

* **Core** (`mw`): Basic utilities, string manipulation, error handling, and process execution (`exec`).
* **Crypto** (`mw::crypto`): Wrappers around OpenSSL for common cryptographic operations.
* **SQLite** (`mw::sqlite`): A C++ wrapper for SQLite3 databases.
* **URL** (`mw::url`): URL parsing, synchronous HTTP requests through
  `mw::HTTPSession`, and coroutine-friendly async HTTP requests through
  `mw::HTTPSessionAsync`.
* **HTTP Server** (`mw::http-server`): An HTTP server implementation based on `cpp-httplib`, including authentication helpers.

== Requirements

* C++23 compatible compiler
* CMake 3.24 or later

== Dependencies

Depending on the modules you enable, you may need the following system libraries installed:

* **OpenSSL** (for `mw::crypto`)
* **SQLite3** (for `mw::sqlite`)
* **cURL** (for `mw::url`)

Internal dependencies handled automatically via CMake FetchContent:

* `cpp-httplib`
* `spdlog`
* `nlohmann/json`
* `googletest` (for tests)

== Usage

You can integrate Libmw into your project using CMake's `FetchContent`.

[source,cmake]
----
include(FetchContent)
FetchContent_Declare(
  libmw
  GIT_REPOSITORY https://github.com/MetroWind/libmw.git
  GIT_TAG main # Replace with a specific tag or commit hash
)
# Enable the modules you need before declaring the content
set(LIBMW_BUILD_URL ON)
set(LIBMW_BUILD_HTTP_SERVER ON)

FetchContent_MakeAvailable(libmw)

add_executable(my_app main.cpp)

# Link against the modules you need
target_link_libraries(my_app PRIVATE
    mw::mw
    mw::url
    mw::http-server
)

# Note: For the core 'mw' library, you currently need to explicitly add the include directory
# if you are using 'mw::mw' directly. Other modules export their include paths automatically.
target_include_directories(my_app PRIVATE ${libmw_SOURCE_DIR}/includes)
----

== Configuration Options

The following CMake options are available to control which modules are built:

|===
| Option | Description | Default

| `LIBMW_BUILD_TESTS` | Build unit tests | `OFF`
| `LIBMW_BUILD_URL` | Build `mw::url` module | `OFF`
| `LIBMW_BUILD_SQLITE` | Build `mw::sqlite` module | `OFF`
| `LIBMW_BUILD_CRYPTO` | Build `mw::crypto` module | `OFF`
| `LIBMW_BUILD_HTTP_SERVER` | Build `mw::http-server` module | `OFF`
|===

== URL HTTP Clients

The `mw::url` module provides two cURL-backed HTTP clients:

* `mw::HTTPSession` performs synchronous requests and stores the latest
  buffered response in the session.
* `mw::HTTPSessionAsync` performs coroutine-friendly requests with one
  internal curl multi driver thread. Async requests return
  `mw::Task<mw::E<mw::HTTPResponse>>`, and the response is returned by value.

For `HTTPSessionAsync`, streaming callbacks run on the internal driver thread,
the session must outlive tasks started from it, and session options are copied
when each request starts.

== Streaming Subprocesses

`mw::Process` uses Linux/glibc 2.24+ `posix_spawnp` and reports launch
failures immediately. Arguments are passed directly without a shell.
Use `execArgs` with string views to validate embedded NUL bytes.

[source,cpp]
----
#include <mw/exec.hpp>

// Exchange bytes with an EOF-aware child using one absolute I/O budget.
mw::E<void> exchange()
{
    auto input = mw::Pipe::create();
    auto output = mw::Pipe::create();
    if(!input) { return std::unexpected(input.error()); }
    if(!output) { return std::unexpected(output.error()); }
    auto process = mw::Process::exec(&*input, {"cat"}, &*output);
    if(!process) { return std::unexpected(process.error()); }
    auto deadline = std::chrono::steady_clock::now() +
        std::chrono::seconds(1);
    auto sent = input->writeUntil("hello\n", deadline);
    if(!sent) { return std::unexpected(sent.error()); }
    if(sent->state != mw::PipeState::COMPLETE)
    {
        // Resume only the unsent suffix; never replay an accepted prefix.
        return std::unexpected(mw::ProcessError{"Write timed out", 0,
                                               sent->bytes_written});
    }
    std::string reply;
    while(reply.size() < 6)
    {
        auto chunk = output->readChunk(6 - reply.size(), deadline);
        if(!chunk) { return std::unexpected(chunk.error()); }
        if(chunk->state != mw::PipeState::COMPLETE)
        {
            return std::unexpected(mw::ProcessError{"No reply", 0});
        }
        reply += chunk->data;
    }
    auto closed = input->closeInput();
    if(!closed) { return std::unexpected(closed.error()); }
    auto done = process->waitUntil(deadline);
    if(!done) { return std::unexpected(done.error()); }
    if(done->state == mw::ProcessWaitState::DEADLINE_EXPIRED)
    {
        auto stopped = process->shutdown(std::chrono::milliseconds(100),
            std::chrono::steady_clock::now() + std::chrono::seconds(1));
        if(!stopped) { return std::unexpected(stopped.error()); }
        if(stopped->state == mw::ProcessWaitState::DEADLINE_EXPIRED)
        {
            return std::unexpected(mw::ProcessError{"Shutdown timed out", 0});
        }
    }
    return {};
}
----

Chunk boundaries carry no framing meaning. `tryRead` returns `WOULD_BLOCK`
when idle; `readChunk` distinguishes data, EOF, and deadline expiry.
Timeouts preserve the child and partial write progress. OS write errors
carry progress in `error.as<mw::ProcessError>()`. Library writes suppress
SIGPIPE per thread, preserve previously pending signals, and leave global
signal dispositions unchanged. A concurrently injected unrelated SIGPIPE
cannot always be distinguished from the signal generated by a write.

`status` queries only the direct child. `waitUntil` waits for child exit
and managed I/O; `shutdown` completes once the direct child is reaped,
with `output_complete` indicating capture EOF separately. Completed waits
are repeatable. Destruction forcibly terminates and reaps the owned child,
then cancels and joins managed I/O. Descendants remain application-owned.
Uninterruptible kernel work can delay forced cleanup.

Serialize lifecycle calls on each process. Only libmw may reap its child;
SIGCHLD auto-reaping and competing reapers are unsupported. One pipe reader
and one writer may operate concurrently. Close an endpoint only after its
I/O returns, and move/destroy a pipe only after all I/O returns. Library I/O
permanently sets the affected endpoint and its duplicates nonblocking;
selected child endpoints must still be blocking (use a fresh pipe).

String input is copied and sent after launch. String capture uses an owned
I/O thread to prevent duplex deadlock and keeps unlimited buffered output.
The destination string must outlive the process and cannot be modified or
accessed concurrently during lifecycle publication. Timed waits publish
partial capture, with copying/allocation overhead proportional to its size.
Use streaming pipes for long-lived protocols and application buffer limits.
External output must be drained concurrently; start pipeline consumers
before waiting on producers. Successful launch closes parent child-facing
pipe ends; a post-spawn failure may also leave those ends closed.

`LIBMW_TEST_SANITIZERS` selects core test instrumentation, defaulting to
`address,undefined`. Use `thread` in a separate build for TSan, or an empty
value to disable it. The library exports its CMake threads dependency.

== Building from Source

To build the library and run tests locally:

[source,bash]
----
# Configure with all modules enabled
cmake -B build -S . \
    -DLIBMW_BUILD_TESTS=ON \
    -DLIBMW_BUILD_URL=ON \
    -DLIBMW_BUILD_SQLITE=ON \
    -DLIBMW_BUILD_CRYPTO=ON \
    -DLIBMW_BUILD_HTTP_SERVER=ON

# Build
cmake --build build -j24

# Run tests
ctest --test-dir build
----
